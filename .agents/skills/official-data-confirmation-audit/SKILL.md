# Skill: Official Data Confirmation Audit Protocol（公式データ確定監査プロトコル v1）

本スキルは、POSTING MAP新地区制作パイプラインにおいて、制作AIが作成した成果物をシステム正本へ昇格（Promotion）または次工程へ引き渡す前に、独立監査AIが**「公式データとして確定できるか」を冷徹に審査・判定するための公式品質ゲートプロトコル**である。

「数字の一致」だけを盲従せず、区割り改定や町丁統合などの構造的な差がある場合にも、**「なぜ違うのか、その意味と公式根拠が完全に解明・確定されているか」** を判定の核とする。

---

## 1. 最上位原則（Absolute Audit Rules）

### ① 根拠が確認できないものはPASSさせない（No Evidence, No PASS）
「たぶん正しい」「大体合っている」「仕様上そうなるはず」等の推測・期待による判定を永久に禁止する。  
**公式一次資料 ➔ 照合 ➔ 整合 ➔ 確定** の全プロセスが客観的に証明されたデータのみを PASS とする。

### ② 門前払い（即時REJECT）の7大不純物
以下の要素が1点でも混入しているデータは、いかなる理由があっても正式データとして採用せず、即座に担当AIへ差し戻す：
1. **推測値**: 公式原本に存在しない数値を補間・推計・仮定したもの
2. **出典不明のWeb情報**: 個人ブログ、まとめサイト、真偽不明の二次情報を根拠にしたもの
3. **コピー元地区の残存データ**: 前地区の自治体名、町名、数値、IDの残骸
4. **公式資料の一部だけを見た判断**: 分母・分子の定義（国内＋在外、当日有権者数等）や注記を無視した切り取り
5. **公式資料間の不一致を勝手に解釈したもの**: 資料間の差異を推測で辻褄合わせしたもの
6. **集計方法が説明できない数値**: 算出ロジック、正規化ルール、集約式が再現できない数値
7. **対象地区と対象期間が違うデータ**: 旧区割りのままの集計、基準年次（国勢調査年度等）の混同

## 2. 「確定性」の審査ロジック（構造的差異への対応）

監査AIは、審査対象データを「単純一致データ」と「構造的差異データ」に明確に区別して審査する。

### A. 単純一致（1:1 Match）の確定条件
- 国・都道府県・市区町村の公式一次資料と成果物の数値が、整数・小数第2位まで **100%誤差ゼロ** で一致すること。
- （例: 市選管確定投票率、国勢調査町丁別人口・世帯数）

### B. 構造的差異（Structural Discrepancy）の確定条件
行政区域や選挙区には、区割り改定（10増10減等）・町丁統廃合・小字細分化・島嶼飛び地・水面調査区などによる構造的なズレが不可避に発生する。  
この場合、「無理やり一致させる」ことも「不一致だから即FAILとする」ことも誤りである。  
**以下の3要件が客観的に証明された場合のみ、「正当な差異」として確定（PASS）を認める**：

1. **差異発生の公式根拠の提示**:
   - なぜ差が出るのかが、法令・告示・選管公式発表・統計局定義書等から客観的に説明されていること。
2. **差分の全数・完全内訳の解明（差分ゼロの証明）**:
   - 差異の件数・人口・世帯数・票数の内訳が1件の漏れもなく100%分類・追跡されていること（未解明差分 0）。
3. **集計ロジックの可逆性と再現性**:
   - どのような計算・ジオメトリ融合（`unary_union`）・合算（SUM）によってその数値が導出されたかがコードおよび数式で完全に再現できること。

## 3. 公式データ確定 7関門判定ツリー（Official Decision Tree）

独立監査AIは、受領した成果物に対して以下の7関門を順に適用する。  
**1つでも NO があれば直ちに FAIL（差し戻し）** とする。

```text
［制作AIより検品依頼パッケージ受領］
  │
  ├─ Q1. 公式一次資料の原本が存在し、直接確認できるか？
  │      └─ NO ➔ 【FAIL】(出典不明・根拠なし)
  │
  ├─ Q2. 複数層（国・県・市）の情報と突き合わせて矛盾がないか？
  │      └─ NO ➔ 【FAIL】(公式資料間不一致・勝手な解釈)
  │
  ├─ Q3. 対象選挙区・対象自治体の範囲は現行規定と完全に一致しているか？
  │      └─ NO ➔ 【FAIL】(対象地区違い・区域誤認)
  │
  ├─ Q4. データの基準時点・選挙回次・年度は正確に合致しているか？
  │      └─ NO ➔ 【FAIL】(時点の混同)
  │
  ├─ Q5. 不一致や集約がある場合、その理由と集計方法は100%説明可能か？
  │      └─ NO ➔ 【FAIL】(説明不能な数値・未解明差分あり)
  │
  ├─ Q6. コピー元地区（旧地区）の残骸・コード汚染・ハードコードは 0 件か？
  │      └─ NO ➔ 【FAIL】(前地区データ残存)
  │
  └─ Q7. POSTING MAPの「正式データ」として後戻りなく採用できるか？
         ├─ NO  ➔ 【FAIL】(品質基準未達)
         └─ YES ➔ 【🎉 PASS】(正式データ認定・次工程への引き渡し承認)
```

## 3.5 3大検証の定義と責務境界 (Three Verification Pillars)

監査AIは、検証対象の性質に応じて以下の3大検証を明確に区別し、混同してはならない：

| 検証種別 | 証明すること | 対象と手段 | 必要証跡 |
|:---|:---|:---|:---|
| **① Registry テスト** | モック条件下での Runtime 動作・Gateway ルーティング検証 | `node tests/test_registry_provisioning_gate.mjs`（Gate 1〜7） | テスト実行ログ（ALL PASS） |
| **② RUNBOOK 実環境証跡** | 対象環境（本番GAS・Spreadsheet）の設定・データ・稼働状態 | RUNBOOK §4「District Production Acceptance Gate」（全20項目実機検査） | 実機E2Eログ、スクリーンショット、Cloud Logging、導通確認記録 |
| **③ データ整合検証** | CSV・GeoJSON・JSON 等の件数、キー、対応関係の完全整合 | 静的データ突合（行数 $N$ ＝ Feature数 $N$、`rowId` 1:1 対応、自治体名完全一致、前地区残骸 0 件） | データ整合検証レポート（件数・キー突合表、残骸ゼロスキャン結果） |

## 4. 多層照合の適用基準（データ種別ごとの最小構成）

全データに一律「3層」を強制するのではなく、公表主体に応じて必要な層を最小限で照合する：

| 対象データ種別 | 照合する層の組み合わせ | 必須確認事項 |
| :--- | :--- | :--- |
| **① 人口・世帯数** | **【国 ＋ 市】 (2層照合)**<br>・国: 総務省統計局 (e-Stat小地域原本)<br>・市: 自治体公式町丁字別人口・世帯数集計 | ・基準年次（国勢調査年度）の合致。<br>・原本属性（`JINKO`, `SETAI`）の直接導出。<br>・原本合計値とGeoJSON全Feature合算値の誤差ゼロ。 |
| **② 選挙データ** | **【国 ＋ 県 ＋ 市】 (3層完全突合)**<br>・国: 総務省選挙部 (全国結果調)<br>・県: 都道府県選管 (開票区別開票結果調)<br>・市: 各市区選管 (開票区内訳・確定投票結果) | ・選挙区計: 国公表値 ＝ 県選管公表値。<br>・自治体内訳: 県選管計 ＝ 市選管公表値合算。<br>・区割り改定がある場合、当時公表値と現行区域再集計値の双方が証明されていること。 |
| **③ 住所・行政境界** | **【県/国 ＋ 市】 (2層照合)**<br>・国/県: 公職選挙法別表(選挙区区域)<br>・市: 自治体公式公称町名台帳・オープンデータ | ・対象自治体が当該選挙区に100%属していること。<br>・町名・大字名が自治体の公称町名台帳と一致していること。 |

## 5. 各工程における確定審査仕様

### Gate 1: 地区データ層確定審査 (District Data Gate)
- **対象**: `data/address_master.csv`, `data/municipality_master.csv`, `data/boundaries.geojson`
- **原本**: e-Stat国勢調査小地域境界（Shapefile/DBF）原本 ＋ 自治体公式公称町名
- **PASS条件**:
  1. `address_master.csv` の行数 N と `boundaries.geojson` のFeature数 N が完全一致（Rule-01）。
  2. 人口・世帯数属性が全Featureに存在し、非負整数であること（Rule-07）。
  3. 原本Feature数とSSOT数の差分について、集約・融合の内訳が100%解明されていること。
  4. 原本自治体人口・世帯数合計と、GeoJSON全Featureの人口・世帯数合計が **誤差 0** であること。
  5. データ整合検証（CSV有効行数、GeoJSON Feature数、自治体別町丁目数合計の完全突合、前地区残骸ゼロスキャン）が完了し、不整合ゼロのデータ整合検証レポートが記録されていること。

### Gate 2: 選挙データ層確定審査 (Election Data Gate)
- **対象**: `data/election_history.json`
- **原本**: 総務省資料（国） ＋ 都道府県選管開票結果（県） ＋ 市区選管開票内訳（市）
- **PASS条件**:
  1. 直近3回分の衆院選小選挙区について、全国・選挙区・自治体別の数値が3層突合されていること。
  2. 投票率の定義（国内＋在外、当日有権者数）が全回次・全自治体で統一されていること。
  3. 区割り改定がある場合、当時公表値と現行区域再集計値の双方が証明されていること。
  4. 前地区の選挙データ残骸が 0 件であること。

### Gate 3: Hアプリデータ層確定審査 (Field App Gate)
- **対象**: GAS本番環境、スプレッドシート、`deployment.json`、`data/config.js`（`active/` 内は完全無改変）
- **原本**: スプレッドシート名（地区名SSOT） ＋ `data/address_master.csv`
- **PASS条件**:
  1. スプレッドシート名が地区名と完全一致し、GASがスタンドアロン展開されていること。
  2. `DATA_DICTIONARY.md` 準拠のシート構造（初期プロビジョニング時 11 Core Sheets 複製、現場2シートオンデマンド生成による 13シート標準構造）が確立され、総ピン数・分母が `address_master.csv` と完全一致すること。
  3. 業務シート（実績・名簿等）に前地区の残骸や不要なテストデータが一切ないこと（初期ゼロ状態）。
  4. 機械的受入ゲート（`node tests/test_registry_provisioning_gate.mjs`）ALL PASS、RUNBOOK §4「District Production Acceptance Gate」全20項目 PASS、実機ブラウザE2Eで全ピン描画・エラー0件、`active/` 配下に改変がないこと。

### Gate 4: ダッシュボードデータ層確定審査 (Dashboard Gate)
- **対象**: `active/manager/manager.js`、ダッシュボード本番画面
- **原本**: `data/boundaries.geojson` ＋ `data/election_history.json` ＋ GAS WebApp API
- **PASS条件**:
  1. 地図ピン・境界ポリゴン選択時、`boundaries.geojson` の実人口・実世帯数がKPI反映されること。
  2. 選挙分析パネルに `election_history.json` の確定値が正しくバインドされていること。
  3. 旧地区キーやダミー計算が残存せず、Console/Network エラーが 0 件であること。

### Final Gate: 全体完成確定審査 (System Final Gate)
- **対象**: リポジトリ全体
- **PASS条件**:
  1. 全レイヤー（CSV、GeoJSON、GAS、Hアプリ、Dashboard）で地区名・件数・数値に一切の矛盾がないこと。
  2. `active/`（コード本体）に地区固有の文字列・ID・URLが 0 件であること（Grep機械監査）。
  3. 可避な手作業要求の排除 (Zero Avoidable Manual) 原則が守られ、不可避な外部リソース投入・初回管理者認証を除き、人間に設計不備に起因する手動入力を一切求めていないこと。

## 6. Handover受領 と Audit Record出力仕様

### ① 制作AIからの受領物（Handover Package）
監査AIは、制作AIから以下の4項目を受領する。不足時は即 REJECT とする：
1. **審査対象工程と成果物パス**: 対象ファイル一覧
2. **照合元公式一次資料一覧**: 発行元、資料名、ファイルパスまたはURL、原本公表数値
3. **公式照合・整合対照表**: 項目名、原本値、成果物値、差分（0または解明された理由）
4. **機械検証・実機実行ログ**: 実行スクリプト、終了コード（Exit Code 0）、エラー0件の証跡

### ② 監査AIの出力物（Audit Record）
審査結果は `.agents/records/record-XXX-[district]-gate[N]-audit.md` として記録する：
- **審査日時・監査官署名・対象工程・判定結果（PASS / REJECT）**
- **公式根拠と照合整合性の判定結果**
- **確定審査対照表（項目, 原本確定値, 成果物確定値, 差分・整合理由, 判定）**
- **ガバナンス・機械検証確認結果**
- **監査官の最終判定と指示（PASS承認 または REJECT理由・具体的修正指示）**

## 7. 物理的READ ONLYの厳格執行

1. 監査AIはファイル編集ツールおよびコマンド実行ツールを持たない。
2. 誤りを発見した場合、自分で修正することは絶対に禁止する（必ず制作AIに直させる）。
3. 制作AIと監査AIの兼任は永久に禁止する。
